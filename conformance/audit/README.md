# roe-guard audit v2 conformance vectors

Language-neutral verification vectors for the roe-guard audit record v2
(SPEC §14.7). Any implementation of the audit format MUST reach the same
verdict on every case.

## Layout

```
conformance/audit/cases.json   chain-verification cases
conformance/jcs/cases.json     JCS (RFC 8785 subset) canonicalization cases
```

Files are generated by `conformance/tools/gen_audit_vectors.py`; verify
with `python conformance/tools/gen_audit_vectors.py --check`.

## Chain case format

`{"format": 1, "suite": "audit-v2", "cases": [...]}`. Each case carries:

- `chain`: the audit file contents as line strings (no trailing `\n`).
  A consumer writes each element followed by a newline; an empty string
  is an empty line.
- `checkpoints`: checkpoint lines, or `null`. When not `null`, the
  consumer writes them to a file and passes that path to the verifier;
  checkpoints are verified only when a path is given. A given file with
  no checkpoint line is `CHECKPOINT_MISSING`, like a missing file.
- `public_keys`: `{"sha256:<hex>": "<hex public key>"}` or `null`.
- `expected`: `{"valid": bool, "broken_at_index": int | null,
  "reason_code": str | null}`.

`broken_at_index` is the failing line index (physical lines, empty lines
included); for `CHAIN_TRUNCATED` it is the number of records present;
other checkpoint failures carry the checkpoint `seq`, or `null` when the
line has no non-negative integer `seq`; `CHECKPOINT_MISSING` carries
`null`.

Lines are split on `\n` only: JCS writes U+0085, U+2028 and U+2029 raw.
A v2 line (and a checkpoint line) must be exactly the JCS bytes of its
object followed by `\n`; the same content in other bytes (key order,
whitespace, escapes, `\r`, a missing final `\n`) is `MALFORMED`
(`CHECKPOINT_MALFORMED` for checkpoints).
v1 lines (no `v` key) keep the v1 rules of roe-guard's `AuditLog`: empty
lines before the first v2 line are skipped and `seq` counts records, not
lines. After a v2 line, an empty line is `INVALID_JSON`. Every
checkpoint's `head_hash` must equal the `entry_hash` of the record at its
`seq`; records after the last checkpoint verify (known limit).

## Signing key

The checkpoints are signed with the RFC 8032 §7.1 TEST 1 key. It is a
published test vector, not a secret; never use it in production.

## JCS cases

Each case has `input_json` and either `expected_hex` (the canonical
UTF-8 bytes in hex, written by hand) or `expected_error`:
`UNSUPPORTED_NUMBER` (a float), `INTEGER_OUT_OF_RANGE` (|n| > 2^53−1),
`NESTING_TOO_DEEP` (more than 64 nested arrays/objects) or
`LONE_SURROGATE`. The ordering case is the RFC 8785 §3.2.3 example: keys
sort by their UTF-16 code units, so the emoji (U+1F600) precedes U+FB33.

## Verification order

SPEC §14.7 fixes the failure-code order per v2 line: `INVALID_JSON` →
duplicate or missing key `MALFORMED` → `UNKNOWN_VERSION` →
`UNKNOWN_FIELD` → type or value `MALFORMED` (values outside the JCS
subset and non-canonical line bytes included) → `TIMESTAMP_FORMAT` → `CHAIN_ID_MISMATCH` →
`SEQ_MISMATCH` → `PREV_HASH_MISMATCH` → `ENTRY_HASH_MISMATCH`, with
`VERSION_DOWNGRADE` when a v1 line follows a v2 line. Patterns match the
whole value with ASCII semantics. The checkpoint order is
`CHECKPOINT_MISSING` →
`CHECKPOINT_MALFORMED` → `CHAIN_ID_MISMATCH` → `CHECKPOINT_KEY_UNKNOWN`
→ `SIGNING_BACKEND_UNAVAILABLE` → `CHECKPOINT_SIGNATURE_INVALID` →
`CHAIN_TRUNCATED` → `CHECKPOINT_HEAD_MISMATCH`. Tail truncation without
a checkpoint is a known undetectable boundary.
